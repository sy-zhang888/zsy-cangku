三个概念的关系

Agent、大模型的上下文、Skill 是怎么配合在一起的

一句话记住：Agent 是干活的人，上下文是他面前那块大小固定的工作台，Skill 是他手边那摞按需取用的岗位手册。

一、各管一摊

概念回答什么问题比喻它不负责什么
Agent谁来决定下一步、谁去动手会自己规划的小助手不负责长期记忆，也不自带行业经验
上下文此刻它能看见多少东西固定大小的工作台不是它的知识储备，对话结束就清空
Skill这件事该按什么步骤做手边的岗位手册不会自己执行，要被翻开才起作用

串起来就是：Agent 在上下文这块工作台上干活，干到不会的地方，就去翻 Skill 这本手册。

三、重点一：上下文如何影响 Agent 的工作

1. 上下文就是 Agent 的记事本

Agent 的循环是"想 → 做 → 看"。它看到的东西、想出来的计划，全写在上下文里。下一轮判断"下一步做什么"时，唯一能参考的就是工作台上的内容。上下文里有什么，Agent 就知道什么。

2. 工作台是累加的，所以越干越贵

轮次工作台上的内容这一轮要读的量
第 1 轮目标 + 第 1 步结果小
第 3 轮目标 + 前 2 步全部结果中
第 10 轮目标 + 前 9 步全部结果大

所以 Agent 的步骤越多，后面每一步就越慢、越贵。

3. 工作台写满，Agent 就开始犯糊涂

上下文的状态Agent 的表现
还很空判断准确，记得住一开始定下的要求
用到七八成开始偶尔重复做已经做过的动作
写满最早的要求被挤出去，忘了最初的目标，或卡在某一步反复转圈
又长又杂即使没写满，准确率也会下降（context rot）；关键信息埋在中间最容易被漏掉

4. 工程上的三种对策

对策做法对 Agent 的作用
压缩快满时把前面的对话总结成一小段，带着摘要重新开始保住目标不丢，让 Agent 继续跑下去
分块长文档切成几段分别处理，最后合并避免一次性把工作台塞爆
隔离派一个"子代理"去做探索性的活，只把结论带回来不让过程中的垃圾信息污染主工作台

四、重点二：Skill 如何沉淀可复用的任务知识

1. 沉淀的是"怎么做"，不是"是什么"

Agent 缺的往往不是知识，而是程序性知识——这件事具体按什么流程办、先做什么后做什么、做完怎么检查。Anthropic 的比方是：给 Skill 写内容，就像给新入职的同事写一本入职指南。

沉淀内容举例
流程步骤先查来源，再写解释，最后自检
判断标准什么情况下用这个做法，什么情况下不用
质量门槛交付前必须逐条检查哪几项
现成资源模板、脚本、参考资料

2. "三级加载"让沉淀几乎不占成本

级别什么时候进工作台占多少
第 1 级：名字 + 描述一直挂着每个约 100 token
第 2 级：SKILL.md 正文被触发时建议 5000 token 以内
第 3 级：脚本 / 模板 / 细则用到时才读几乎不占
这是 Skill 设计与上下文之间最精巧的一处配合：你可以沉淀海量的任务知识，而平时它们一点工作台都不占。知识存在文件夹里，用时才搬上来；脚本甚至只把运行结果带回来，代码本身不上工作台。

3. 沉淀的闭环

  • 第一次做某类任务 → 边做边摸索
  • 把做法写成 SKILL.md → 步骤 + 标准 + 检查清单
  • 以后再遇到 → 自动触发，不用重新交代
  • 发现新问题或更好的做法 → 回头改进 Skill 本身

五、三者协同：一个完整的例子

任务：用本仓库的 Skill 生成一份"光合作用"的学习资料。

环节谁在起作用发生了什么
1. 识别任务Skill 第 1 级模型看到 concept-learning-kit 的描述与"学习一个概念"匹配
2. 装载做法Skill 第 2 级 → 上下文正文被读上工作台：先找类比、再查来源、按固定结构输出
3. 取用模板Skill 第 3 级 → 上下文要写 HTML 时，才去读 references/html-skeleton.md
4. 执行循环Agent + 工具检索来源 → 读文件 → 写 HTML → 打开检查，不对就改
5. 记录过程上下文每一步的想法和检索结果堆在工作台上，供下一步参考
6. 收尾上下文管理任务很长时压缩历史，避免工作台写满导致质量下降

Skill 解决"会不会做"，上下文解决"记得住多少"，Agent 解决"能不能自己跑完"。

六、缺一个会怎样

  • 没有上下文：Agent 每一步都是第一次，会原地打转。
  • 没有 Skill：Agent 每次都要你从零教一遍，而且做法不统一。
  • 没有 Agent：Skill 只是一本没人翻的手册，上下文也只是一块没人用的黑板。
